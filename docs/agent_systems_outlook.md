# Тенденции агентных систем: skills and environment engineering  
## Введение: шкала автономности AI-систем

Современные AI-системы образуют непрерывный спектр по степени автономности агента. Выбор точки на этой шкале определяется двумя ключевыми параметрами: **стоимостью ошибки маршрута** и **степенью предсказуемости пути решения**.

```
Свободный агент → ReAct-агент → Workflow-агент → Детерминированная система
 (высокая автономность)                          (полная детерминированность)
```

### Характеристики типов систем

| Тип системы | Маршрут | Стоимость ошибки | Требование к воспроизводимости | Пример |
|---|---|---|---|---|
| Свободный агент | Неизвестен, определяется агентом | Низкая | Низкое | OpenClaw |
| ReAct-агент | Неизвестен, требует трассировки | Средняя | Среднее | Codex, Claude Code |
| Workflow-агент | Известен, фиксирован | Средняя–высокая | Высокое | n8n |
| Детерминированная система | Полностью формализован | Высокая | Максимальное | Классические алгоритмы |

### Критерии выбора

**Свободный агент** применим, когда приоритет — скорость исследования, а человек остаётся в контуре оценки результата. Недетерминированность маршрута допустима, если её цена не затрагивает основной бизнес-процесс.

**ReAct-агент** необходим, когда маршрут нельзя зафиксировать заранее, но система обязана оставлять трассируемый след: выбранные шаги, вызванные инструменты, основания решений. Без наблюдаемости итеративное улучшение системы невозможно.

**Workflow-агент** подходит для повторяемых функций с известной последовательностью шагов. Агентность сохраняется на уровне отдельных шагов; управление общим маршрутом изымается из-под контроля модели.

**Детерминированная система** оправдана там, где задача полностью формализуется правилами. Включение LLM в такой контур добавляет задержку, стоимость и вариативность без компенсирующей ценности.

### Открытый вопрос

По мере массового распространения свободных агентов критическим становится не вопрос повышения их автономности, а вопрос управления рисками:

> **Ключевая проблема:** как ограничить доступы, инструменты и область действия агента так, чтобы стоимость ошибки оставалась приемлемой для конечного пользователя, не являющегося экспертом в оценке агентного поведения.

## 1. Базовая архитектурная идея агентных систем

Агентные системы можно описать через **итеративно-рекурсивную модель решения задач**.

### Итеративность
Работа агента организована как замкнутый цикл управления:

```
reason → act → observe → iterate
```

Это проявляется в разных терминах:

| Подход | Эквивалент |
|---|---|
| ReAct | Thought → Action → Observation |
| Когнитивные архитектуры | Perception → Cognition → Action |
| Кибернетика | Feedback control loop |

### Рекурсивность
Задачи декомпозируются на подзадачи, которые решаются тем же механизмом.

```
goal
└─ subgoal
   └─ subgoal
```

**Вывод:**  
Агентная система — это **иерархия рекурсивных задач, выполняемых через итеративные циклы наблюдения, рассуждения и действия**.

---

## 2. Архитектура агентной системы

Минимальная production-архитектура включает несколько слоёв.

```
Goal / Intent
↓
Reasoning / Control Loop
↓
Skills (CFS)
↓
Tools / MCP (RFS)
↓
Resources
```

Дополнительные production-слои:

- **Runtime / Execution manager**
- **Governance / Guardrails**
- **State / Memory** *(один из наиболее архитектурно сложных аспектов — требует явного определения области видимости памяти: агент, skill, сессия, долгосрочное хранилище)*

---

## 3. Аналогия с телеком-архитектурами

Агентную систему можно интерпретировать через модель сервисов.

| Телеком | Агентная система |
|---|---|
| Product | Выполненная задача |
| CFS | Skills |
| RFS | Tools / MCP |
| Resources | Внешние системы |

**Агент выполняет роль оркестратора сервисов.**

---

## 4. Skills как ключевой строительный блок

Skills можно рассматривать в двух интерпретациях:

### 1. Service-подход
Skills — это **CFS-спецификации**.

### 2. Software-подход
Skills — это **подключаемые capability-библиотеки**.

Обе модели требуют:

- модульности
- контрактов
- версионирования
- управления зависимостями
- каталогизации

---

## 5. Экосистема skills

Зрелая инфраструктура skills требует:

```
skills ecosystem
├─ specification
├─ contracts
├─ versioning
├─ dependency management
├─ catalog / registry
├─ capability semantics
├─ interface typing
├─ discovery
├─ observability
├─ governance / trust
└─ testing / certification
```

Это почти полностью повторяет зрелые **service ecosystems**.

> **Важное ограничение:** в отличие от пакетных экосистем (npm, Maven), верификация skills требует проверки *поведения* в условиях неопределённости, а не только корректности кода. Это качественно усложняет сертификацию и управление доверием.

---

## 6. Сдвиг инженерной парадигмы

В индустрии появляется тенденция к расширению инженерной области:

```
agent engineering → agent engineering + environment engineering
```

Связанные понятия:

- harness engineering
- environment engineering
- skill ecosystems

### Причина
Качество системы всё сильнее определяется:

```
environment
tools
skills
runtime
```

а не самой моделью.

> **Уточнение:** это не замена агентной инженерии средовой, а **расширение зоны ответственности**. Появляется новый инженерный слой, но старый не исчезает.

---

## 7. Новая роль агента

Агент становится **тонким универсальным рантаймом**.

```
Agent runtime
↓
Skill libraries
↓
Tools / MCP
↓
Environment
```

Аналогия с JVM:

```
JVM          →  Agent runtime
Java libs    →  Skill libraries
OS           →  Environment
```

> **Ограничение аналогии:** JVM детерминирован — агентный рантайм нет. Один и тот же skill может вести себя по-разному в зависимости от контекста и модели. Это принципиально усложняет versioning, dependency management и воспроизводимость по сравнению с классическими пакетными экосистемами.

---

## 8. Экосистема skills как аналог package ecosystem

Если skills становятся основной единицей разработки, возникают эффекты, аналогичные экосистемам пакетов.

### Возможные элементы

- skill registries
- dependency graphs
- version compatibility
- trust & security
- marketplaces skills

### Ключевое отличие от пакетных экосистем

В классических экосистемах зависимости разрешаются статически, а корректность верифицируется автоматически. В экосистеме skills:

- поведение skill зависит от модели и контекста
- зависимости между skills могут проявляться динамически, в процессе выполнения
- доверие требует поведенческой, а не только структурной верификации

## 9. Экономика capabilities

Возможная эволюция:

```
agent-centric systems
↓
capability ecosystems
```

где:

- skills — основной актив
- агент — универсальный оркестратор

---

## 10. Роль environment engineering

Environment engineering становится ключевым фактором качества системы, однако не единственным.

Уточнённая модель:

```
Agent quality = f(model_ceiling, environment_quality, skill_design)
```

- **model_ceiling** — потолок, определяемый базовой моделью; среда и skills влияют на то, насколько близко к нему работает система
- **environment_quality** — инструменты, ограничения, структура контекста, правила взаимодействия
- **skill_design** — модульность, контракты, покрытие capabilities

Хорошо спроектированная среда включает:

- инструменты
- ограничения
- структуру контекста
- правила взаимодействия

---

## 11. Важный баланс

Лозунг «agent design is dead» некорректен.

Реальная модель:

```
environment design
+
skill ecosystem
+
stable agent runtime
```

---

## 12. Многоагентные системы

По мере усложнения задач агенты начинают оркестрировать других агентов. Базовая иерархическая модель становится недостаточной:

```
Orchestrator agent
├─ Sub-agent A
│  └─ Skills / Tools
└─ Sub-agent B
   └─ Skills / Tools
```

Это порождает дополнительные архитектурные проблемы:

- делегирование полномочий и доверие между агентами
- согласованность состояния и памяти на разных уровнях иерархии
- отладка и наблюдаемость распределённых агентных цепочек

---

## 13. Итоговая модель

Агентная система может быть описана как:

```
Goal
↓
Recursive task decomposition
↓
Iterative reasoning loops
↓
Skill orchestration (CFS)
↓
Tool invocation (RFS)
↓
Environment interaction
```

---

## 14. Прогноз

Если текущие тенденции сохранятся, вероятны следующие изменения:

1. Появление **крупных экосистем skills**
2. Формирование **стандартов интерфейсов skills**
3. Развитие **skill registries и marketplaces** *(с необходимостью решить проблему поведенческой сертификации)*
4. Укрепление **environment engineering** как самостоятельной инженерной дисциплины
5. Стабилизация **универсальных агентных рантаймов**
6. Формирование практик управления **многоагентными иерархиями**

---

## 15. Ключевая гипотеза

Будущее агентных систем может выглядеть так:

```
Stable agent runtime
+
large capability ecosystem
+
well-designed environments
```

где агент — это **универсальный интерпретатор целей и оркестратор capabilities**.

> **Оговорка:** реализация этой модели требует решения проблем недетерминированности, поведенческой верификации skills и управления доверием в многоагентных иерархиях — задач, для которых классические инженерные паттерны применимы лишь частично.
